Capability auth, fixed-origin checks, limited request sizes/timeouts and process-local rate limits exist (`internal/chat/http.go:133-154,205-275,339-364,440-549,571-628`). ### Release blockers, ranked

**P0 — block public traffic; each item needs explicit closure.** For each item, the cited contract impact needs project-foundation coordination with the backend/widget owners before editing published behavior (`docs/architecture/context-map.md:9-14,20-31`).

1. **No actual handoff or recoverable human queue.** The only legal stored outcome is `delivery_not_wired`, and the visitor is explicitly told no email was sent (`docs/contracts/chat.md:92-106`; `database/migrations/002_escalation.sql:7`; `internal/chat/escalation.go:127-162`; `internal/chat/http.go:614-628`; `web/assets/widget.html:32-42`). `LocalEmailOutbox` is volatile, bounded to 100, not exposed to an operator, and its error is ignored after persistence. There is no staff UI or staff API. A ticket in the DB is **not** a human handoff. **Owner:** chat-backend for durable delivery/queue and status, chat-widget for consent/response copy, project-foundation for additive escalation contract; user names a real support operator and mailbox. **Local acceptance:** fixture mail transport/outbox with failure/timeout/ambiguous acknowledgement, crash/restart/replay, duplicate suppression, backlog and operator acknowledgment tests; verify truthful states (accepted for dispatch ≠ delivered to inbox ≠ read by human), with messages reflecting observed state and no false “sent.” **External gate:** choose SMTP/transactional mail provider, credentials/domain/SPF-DKIM-DMARC and a support inbox; authorize a real, controlled end-to-end delivery/receipt test. Without a staff UI, adopt a **restricted mailbox queue**: designated staff receives sanitized notifications, accesses full necessary ticket data through an access-controlled operator procedure, owns daily triage, handling/retention and outage fallback. A direct `SELECT`/dump of the production DB or a public ticket endpoint is not a safe substitute. If that workflow cannot be staffed, postpone release or explicitly redefine/remove “human support by email”; do not keep a button promising human support with nobody reading tickets. Keep a recorded-not-sent fallback only if its operational collection/recovery and visitor wording are explicitly approved.
2. **No production knowledge or proven production AI availability.** Only fictional `example.org` seed material is provided (`README.md:27-34`, `internal/chat/store.go:430-445`); missing key gives 503 for questions matching knowledge (`internal/chat/provider.go:74-81`; `README.md:23,38`). Lexical overlap/citations are not semantic accuracy checks (`docs/contracts/backend.md:83-89`; `README.md:50-51`). **Owner:** chat-backend (curation/retrieval/provider evaluation), project-foundation (provider/privacy contract), user (approves content/provider/budget). **Local acceptance:** versioned approved organization corpus, withdrawal tests and a reviewer-owned question set covering supported/unsupported/adversarial/expired policy; test actual provider configuration with sanitized evaluations under separate authorization, fail closed and monitor error/spend. **External gate:** provider account/server-side secret and billing/limit authorization, data-processing terms and content approver; select accurate provider wording instead of hard-coded OpenAI disclosure (`web/assets/widget-core.mjs:45`). No production seeding from `--seed-demo`.
3. **Hosted persistence and recoverability unproven.** SQLite is default local-file DB and `serve` migrates it automatically; remote Turso needs URL/token and separately authorized `migrate --allow-remote`; tests use fixtures, not a real remote (`cmd/assistant/main.go:43-78`; `README.md:40-41`; `internal/chat/turso.go:24-37`; `docs/contracts/backend.md:77-81`). There is no checked-in backup/restore, remote migration rehearsal/rollback, or retention process; migrations are split independently atomic statements (`internal/chat/store.go:62-88`). **Owner:** chat-backend storage + project-foundation operations, user picks managed DB/account. **Local acceptance:** ephemeral isolated database with same schema/fixture, idempotent migration/restart and restore drill on non-production data, schema version check, isolation/replay and negative paths; explicit deployment-time migration plan. **External gate:** provision authorized hosted DB/secret, backup and restore policy, staging/live compatibility smoke without reseeding existing data. A single durable appropriately backed-up SQLite host could be separately designed; do not assume Turso is mandatory, but do not call the current local file production-ready.
4. **No deployment, TLS or verified host integration.** Server defaults to loopback HTTP and serves a public sample host at `/`; origin/CSP parent allowlists must be set explicitly and host CSP must permit script/style/frame (`cmd/assistant/main.go:83-111`; `internal/chat/http.go:97-112`; `web/README.md:5-19`). Origin restrictions are not identity or non-browser abuse defense (`docs/contracts/chat.md:65-74`). **Owner:** project-foundation deploy/config with chat-backend HTTP and chat-widget embedding; user owns domain/host. **Local acceptance:** immutable staging build behind a proxy that terminates HTTPS, validates actual `ASSISTANT_ORIGIN`, `WIDGET_PARENT_ORIGINS`, external host CSP/frame ancestry, proxy IP policy, no secret in asset/URL/log, stale asset/cache and health/restart behavior; gate `/widget/sample-host.html` and root sample redirect from being mistaken for the real site (disable or explicitly brand/limit them). **External gate:** domains, DNS, TLS certificate, target hosting, canonical visitor host/origin and permitted third-party script policy; staging then controlled deployment approval.
5. **Public abuse and spending limits insufficient.** Current 10 creations/30 messages/10 escalations per minute are process-local by direct peer IP, reset on restart; behind an ordinary reverse proxy all users may appear to share its IP, while spoofed forwarding headers are intentionally ignored (`internal/chat/http.go:205-275`; `docs/contracts/chat.md:70-74`; `.scratch/support-escalation/evidence/independent-acceptance.md:108-113,175-180`). Provider concurrency is capped at 8 but there is no durable/global budget, automated-traffic mitigation or sender-abuse protection. **Owner:** chat-backend + project-foundation deployment/security; user sets traffic and spend ceilings. **Local acceptance:** proxy-aware *trusted-boundary* tests for real peer identity and spoofed headers, global/distributed or edge limit tests under restart/multi-request load, mail flooding and cost cap/fail-safe scenarios; never trust arbitrary `X-Forwarded-For`. **External gate:** edge/WAF/rate service and alerts, provider and mail quota controls, threat/incident owner.
6. **Privacy/retention and support accountability undefined.** Conversation text, visitor email and optional note persist (`database/migrations/001_initial.sql:2-28`, `database/migrations/002_escalation.sql:1-12`); guest reload intentionally loses access but does not delete history (`web/assets/widget.html:17-20`, `README.md:25`). No schema or service deletion/export/retention workflow appears in these migrations or API routes (`internal/chat/http.go:88-95`). Capability possession grants whole conversation history (`docs/contracts/chat.md:15,74`); explicit escalation consent only permits storage, not an undisclosed new mail recipient/purpose. **Owner:** user/privacy operator decides policy; chat-backend deletion/export/retention/access-control, chat-widget disclosures, project-foundation contract. **Local acceptance:** documented data map and lifespan, consent/copy matching actual recipients/provider, deletion and access-request workflow incl backups, secure operator authorization/audit and no transcript/PII in telemetry; tests verifying aging/removal and capability isolation. **External gate:** privacy notice, jurisdiction/processor agreements, retention schedule, breach/subject-request contact and legal review as appropriate. Do not infer compliance from no-store responses or hashed bearer tokens.

**P1 — acceptance/operability gates before go-live (also no-go if unresolved).**

7. **No production observability/on-call runbook.** Startup/error logs are minimal (`cmd/assistant/main.go:64-76,111-123`); fixed safe client errors are good (`internal/chat/http.go:157-184`) but there are no service-level metrics, alerting for provider/storage/mail failures, stuck tickets or spend, nor documented owner response. **Owner:** project-foundation operations + chat-backend safe counters; user names on-call and response hours. **Local acceptance:** synthetic failure exercises yield non-sensitive health/error counters, pending-mail age and queue depth, alert routing, backup restore and rollback runbook with no email, token, transcript or provider payload logging. **External gate:** monitoring/alert destination, operator coverage, incident escalation, backup targets.
8. **Cross-origin browser, accessibility and user wording need final-site acceptance.** There is real offline Chrome escalation/browser evidence and UI-01 cross-origin visual evidence, not production hostname/CSP/provider/mail proof (`.scratch/support-escalation/evidence/independent-acceptance.md:10-16,175-180`; `.scratch/widget-visual-refresh/issues/01-corner-widget.md:32-39`). Iframe is capped and narrow screens scroll internally; 200% zoom and arbitrary host CSS overrides are untested; same-frame source links may lose guest chat (`web/README.md:21-23,84-86`). Demo/fictional wording remains in shipped iframe (`web/assets/widget.html:13-20`). **Owner:** chat-widget with project-foundation host contract; user accepts brand/accessibility content. **Local acceptance:** Chromium plus at least one additional real browser on final staging host, keyboard/screen-reader review, focus/open-close/escape, 200%/400% zoom, 320px/mobile, dark/reduced-motion, real consent and truthful mail states, CSP spoof rejection and source-link behavior; verify no accidental loss of controls. **External gate:** final host page and content/branding sign-off; assistive technology/browser availability.

### Bounded implementation order and dependencies

1. **Release decisions/contract brief (user + orchestrator → foundation).** Fix hosting/domain, DB durability choice, provider and content approver, mailbox+named staff workflow, mail transport, retention/privacy terms, spend/traffic caps and on-call. Specify visitor-visible states and whether undelivered persisted tickets will be manually recovered; update `docs/contracts/chat.md` and backend/embedding contracts *before* backend/widget changes. Acceptance: signed-off scope, exact outcome/state table and ownership for each failure/retry/duplicate case. No credentials in task briefs.
2. **Backend durable handoff + restricted operator process (chat-backend, foundation contract review).** Mailer with durable status/outbox/idempotency and bounded retry; managed or supervised operator review without a staff UI; authorization/audit, monitoring and outage fallback. Acceptance: local fake-transport/crash/replay/failure tests, inbox/operator runbook, then user-authorized staging real-delivery test. Coordinate new statuses with widget; the existing `delivery_not_wired` schema constraint needs an additive migration, not an undocumented update (`database/migrations/002_escalation.sql:7`).
3. **Approved knowledge/provider + hosted DB (chat-backend; user approves documents/accounts).** Safe import/withdrawal and evaluation, separate staging migration/restore and persistence smoke, secret injection. Acceptance: source-reviewed answer suite, unsupported cases, real hosted-provider and DB smoke only after explicit authorization, no demo seed; prove restart, rollback and isolation.
4. **Deployment hardening + privacy/operations (project-foundation coordinating backend/widget).** TLS proxy, canonical origins/CSP, edge abuse/spend policy, backups/retention, telemetry/alerts and incident/rollback procedure. Acceptance: staging negative origin/proxy/budget cases, recovery/alert drills, approved privacy notice and operator staffing.
5. **Final widget/release gate (chat-widget + independent validator; orchestrator decides).** Align real-mail and provider disclosures, remove demo branding, rerun browser/accessibility matrix against the *actual* host and final version; run `make format`, `make lint`, `make static`, `make unit`, affected `make contract`, `make fuzz-smoke` for changed boundaries and `make fuzz-full` before release (`docs/testing/testing-contract.md:15-21`). Independent release evidence must separate local fixtures, authorized staging live integrations and public production checks. Only the user/orchestrator can approve commit, push and deployment.
